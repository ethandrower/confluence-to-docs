**Do not merge #55/#56/#58 individually.** #56 and #58 each add a migration
numbered `0033` on parent `0032`. The filenames differ, so git merges them
without reporting a conflict and you end up with two leaf nodes — Django then
refuses to migrate, and it fails in the **release** phase of a Dokku deploy, not
at build. Per-PR CI cannot catch it because each PR is only ever tested alone,
and all three are green.

#59 fixes this (renumbers #58's to `0036`) and resolves four real conflicts.
Merge order: **#59 first, then #60, then close #55/#56/#58** rather than merging
them.

## Priscilla's three blockers → where the code is

**1. Admin permissions** — "can't request docs from customers without admin
access." She has **no portal account on production**. `STAFF_EMAIL_DOMAINS` is
`citemed.com`, and our own people are auto-provisioned as agents on first
sign-in, so if her address is `@citemed.com` this needs no grant at all — just
send her a link:

```bash
dokku run citemed-docs python manage.py magic_link --email <her>@citemed.com
```

If her address isn't on that domain, she needs a `PortalUser` with `role=admin`
created by hand. Do not add another domain to `STAFF_EMAIL_DOMAINS`.

**2. User list submission/configuration** — built, in **#60**. Customers fill in
their own roster at `/users`: a row per person, module access and access type, or
they upload the spreadsheet they already keep (CSV or Excel, with a template we
hand out, a column-mapping confirmation step, and an async import). CS opens one
with `manage.py user_request --open <company>`, then `--provision` to create the
accounts and `--invite` to email them. Those are two separate commands on
purpose: provisioning never emails.

**3. Backend folder configuration** — built, in **#56**. Staff can create
folders inside a customer's tree that belong to us (`POST
/api/admin/files/folders/`), nested up to 8 levels, read-only to the customer.
That is the SharePoint-shaped structure she's asking for — "Reference Libraries"
and "PDFs" as staff-owned folders, with the customer's own uploads kept separate
by `Bucket.origin`.

So #2 and #3 are a deploy away, not a build away.

## How to deploy and verify

```bash
git push dokku main                                    # after #59/#60 merge
dokku run citemed-docs python manage.py smoke \
    --url https://support.citemed.com                  # nine checks, non-zero exit on failure
```

The smoke command is the gate worth trusting — it walks health, SPA shell,
static assets, anonymous refusal, magic-link sign-in, session identity, file
tree, ticket list and sign-out. Re-run CI after any rebase: the green check on
an un-rebased branch no longer describes the merged tree.

To see the staff→customer share working end to end without building it by hand:

```bash
dokku run citemed-docs-staging python manage.py seed_share_demo
```

That seeds Acme Devices with a staff-owned `Reference Library / PDFs` tree
(exactly the shape in blocker 3) and prints a sign-in link per person — Ana to
push as staff, Jane or Raj to see the read-only customer view.

## Known state worth knowing

- **Seven known defects** are tagged in `qa/qase/support-portal-cases.yaml` (60
  manual cases, 7 suites). The one that matters most: **raising a site notice
  emails nobody** — `SiteNotice` only broadcasts over WebSocket, so the only
  notice channel is unreachable during the incident it describes. Pre-existing,
  not a regression from any of these PRs. Scoping for the fix is in
  `docs/notices-and-campaigns.md`.
- The 60 QA cases are **not yet in Qase** — blocked on `QASE_TESTOPS_API_TOKEN`.
  Project code is `CSP`; `QAC` is the hiring-challenge sandbox, don't reuse it.
- **No new config vars** are needed by any of this. The only settings change is
  `SECURE_HSTS_SECONDS`, which is defaulted.
- The RevenueHub integration is a **pull** endpoint (`/api/v1/share-events/`).
  If RevenueHub's consumer isn't built, nothing breaks — it just sits unused.
- There is **no staff UI** for the user request form yet; the admin API and
  `manage.py user_request` are the staff surface.
- An earlier session printed the host-global AWS secret key into a transcript
  via `dokku run <app> env`. **It should be rotated**, and the replacement
  scoped to the staging bucket only. Staging must never point at the production
  fileshare bucket `citemed-fileshare`, which holds real customer files.

## Open decisions (not blockers)

1. **Role vocabulary.** There are now three: RevenueHub's
   `reviewer/writer/qa/admin/viewer`, the portal's `owner/admin/customer`, and
   the customer-facing `Admin / Fulfiller-Edit / Viewer` on the request form.
   The form's set is the one customers read. Mapping lives in exactly one place
   (`RequestedUser.ROLE_TO_PORTAL_ROLE`) and currently maps **everything** to
   `customer` — because `PortalUser.role='admin'` is a *CiteMed staff* role, and
   letting a customer pick it would hand them cross-tenant access.
2. **Module entitlement.** `Company.licensed_modules` is an interim allowlist
   (empty = everything) until ECD-2589 lands.
3. **Notice email.** Whether service notices go out via the service path or
   DeftMarketing decides which repo the composer lives in.
